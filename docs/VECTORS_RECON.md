## 2. Формат qwen3-дампа

Проверено Range-запросами: первые 3 МБ, кусок в середине (230 МБ), последние 300 КБ.

- В файле только операторы `UPDATE knowledge_base_chunks SET embedding_qwen3_embedding_4b = '[...]' WHERE id = N;`.
- Текста, страницы и документа в нём нет. Это дополнение к основной таблице, соединять нужно **по `id`**.
- Тип значения: текстовый литерал `[a,b,c,...]`. Это формат pgvector `vector(2560)`, не base64.
- **Размерность 2560** (посчитано на 3 разных рядах: начало, середина, конец).
- Числа с точностью fp16/bf16 (например `0.03100586`). Вектор нормирован: ||v|| ≈ 1.00002, значит cosine = скалярное произведение.
- Колонка называется `embedding_qwen3_embedding_4b`, имя модели прямо в ней.
- Число рядов: id идут подряд от 1 до **14 577**. Последний `WHERE id = 14577` виден в конце файла. Средний ряд 32 608 Б, 14 577 × 32 608 ≈ 475 МБ, что совпадает с размером файла.
- `drugs_chunks_qwen3.sql` в том же формате (`UPDATE drugs_chunks ... WHERE id`), около 1,1 тыс. рядов по оценке размера.
- Старая колонка `embedding` в дампах чанков: **1536-мерная**. Это другая модель, к qwen3 отношения не имеет и не нужна.

## 3. Какая именно модель

Три независимых подтверждения:

1. Имя колонки: `embedding_qwen3_embedding_4b`.
2. Размерность 2560 равна размерности Qwen3-Embedding-4B (0.6B даёт 1024, 8B даёт 4096).
3. Практическая проверка. Я взял чанк id=2489 (текст из `a2b3c4d5e6f7_init`), отправил его **один раз** в RouterAI `qwen/qwen3-embedding-4b` и сравнил с сохранённым вектором. Размерность ответа 2560, cosine **0.9998**, расхождение объясняется округлением до fp16.

Файлы `qwen.flag` в `VetAI/knowledge/galen/preparations/N/` к эмбеддингам отношения не имеют. Содержимое: `qwen pipeline v1 / sections=8 / inserted=8`. Это отметка LLM-конвейера, который разбирает карточки препаратов. Рядом лежат `deepseek.flag`, `tesseract.flag`, `vsegpt.flag`, `overlap.flag`. `VetAI/README.md` описывает только структуру бакета.

## 6. sqlite-vec

- Окружение: Python 3.13.3, SQLite 3.49.1, `enable_load_extension` доступен, numpy 2.2.5.
- На PyPI sqlite-vec **0.1.9** с колесом `sqlite_vec-0.1.9-py3-none-win_amd64.whl`, подходит под наш Python. Установка не делалась.
- Объём при 14 577 чанках × 2560 измерений:

| Хранение | Размер |
|---|---|
| float32 | ≈ 149 МБ |
| float16 (в numpy-файле) | ≈ 75 МБ |
| int8 (sqlite-vec) | ≈ 37 МБ |
| float32, усечение до 1024 (MRL) | ≈ 60 МБ |

  Текущий `data/index.db` занимает около 106 МБ.
- Для ~14,5 тыс. векторов полный перебор достаточно быстр, ANN-индекс не нужен. Как вариант можно обойтись без расширения: матрица float16 в `.npy` и `numpy.dot` (с предвыборкой по page_index, см. ниже).
- Усечение (MRL) и int8-квантование изменят качество. Для 2560 → 1024 на нашем корпусе качество нужно измерить отдельно, я не проверял.

## 7. Конвейер «онтология → главы → векторы внутри глав»

1. Онтология даёт главу как диапазон страниц `[p_start, p_end]` (page_index, 0-based).
2. Фильтр чанков: `source_document_id` → наш `source_id`, `page_number - 1 BETWEEN p_start AND p_end`.
3. Эмбеддинг запроса из RouterAI, cosine по отфильтрованным чанкам, top-k. В 0-based индексе страниц нужно учесть, что чанк, начинающийся на странице N, иногда заходит на N+1.
4. Результат показывается как страница `page_index` с подсветкой, в рамках существующего интерфейса.

Для фильтра нужна таблица `chunks(id, source_id, page_index, chunk_number, content?)` и векторы по `id`. `content` можно не хранить, если показывать страницу из `pages`.

## 9. Риски

- **Разбор дампов.** При разборе потоком по регулярному выражению не распознались: sd 14 (0 рядов из 745 КБ) и один чанк id=6170 в sd 8. Формат полей немного различается (в `a2b3c4d5e6f7_init` числа в кавычках, в других без кавычек). Скрипту нужен устойчивый разбор, лучше `psycopg`-подобный парсер или проверка числа рядов против `COUNT`.
- **sd 13 (id 6887–11697, около 4800 чанков) целиком не разбирался.** Дамп 98 МБ я не скачивал. Диапазон id получен как «дырка» между разобранными файлами (6887–11697) и по замеченному ряду id=8239. Нужно проверить при загрузке.
- **Соответствие документов не полное.** Для sd 10 и 11 нет слагов в `SDOC_SLUG`, у статей (sd 22+) нет `page_number`. Статьи придётся связывать по названию.
- **Привязка чанка к странице неточная.** Один номер на чанк, чанки иногда заходят на соседнюю страницу. Для фильтра по главам нужен запас ±1 страница.
- **Различие между нашими страницами и страницами старой системы.** Проверено выборочно на sd 1, 15, 16 (смещение ровно −1). Для остальных источников смещение не проверялось, в частности для sd 13 и 17 текст чанков не нашёлся в моей короткой выборке. Нужна полная сверка при загрузке (по тексту).
- **Точность.** Сохранённые векторы fp16-округлены, поэтому cosine с эталоном 0.9998, не 1.0. Для ранжирования это несущественно.
- **Префикс запроса.** Не проверен на качество поиска, см. раздел 5.
- **Зависимость от сети.** При недоступности RouterAI вектор запроса не получить, нужен запасной путь (FTS5 уже есть).
- **Секреты.** Ключи доступа к S3 не записаны в проект. Для загрузки их нужно передавать через переменные окружения.
