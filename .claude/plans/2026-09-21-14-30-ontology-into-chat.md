# План: интеграция онтологии («смысловых оглавлений») в чат-ассистента VetAI

## Цель и контекст

Директор хочет «поиск без векторов»: чат-ассистент перед контентным FTS-поиском
читает карту онтологии (по-книжные и по-главные аннотации), чтобы подсказать
модели релевантные книги/главы со страницами и отвечать точнее.

Сейчас чат работает в inline-режиме (`backend/app/routers/chat.py::_run_inline`):
1. LLM извлекает 2-5 ключевых слов (`_extract_keywords`);
2. FTS-поиск по контенту (`_run_search`: AND, при <3 сильных хитах домешивает OR);
3. LLM формирует короткий ответ по найденным хитам.

Онтология (`ontology_fts`, 648 строк: 23 книги + 625 глав) в этот поток пока
НЕ включена. Есть готовый эндпоинт `GET /api/ontology/search`
(`backend/app/routers/ontology.py`) и вкладка «Онтология» во фронте.

Задача — ДОПОЛНИТЬ поток онтологией, не заменяя контентный FTS и не добавляя
новых LLM-вызовов: ontology-поиск это локальный SQL по уже открытому read-only
соединению, переиспользующий уже извлечённые ключевые слова.

## Архитектурные решения

1. **Вынести общую SQL-логику ontology-поиска в переиспользуемый модуль.**
   Сейчас SQL (`_SQL`, `_row`, `_run` + AND→OR добор) живёт приватно внутри
   `routers/ontology.py`. Чтобы не дублировать SQL в chat.py и не тянуть роутер
   из роутера, вынести ядро в отдельный модуль (предлагается
   `backend/app/ontology.py`, рядом с `db.py`/`history.py`/`llm.py`):
   - функция вида `search_ontology(db, q, limit) -> List[dict]` — инкапсулирует
     `build_match_query` → `_run` → добор `build_or_match_query` (текущая логика
     из `ontology.py::search`, но принимает готовое соединение `db`, а не
     Depends).
   - `routers/ontology.py::search` становится тонкой обёрткой над этой функцией
     (сохранить текущий JSON-контракт эндпоинта 1:1, вкладку «Онтология» не
     ломать).
   Обоснование: минимальная инвазивность, единый источник SQL, chat.py вызывает
   ту же функцию по своему `connection()`.

2. **Онтология — отдельный блок контекста, НЕ смешивается с контентными хитами.**
   В `_run_inline` после извлечения ключевых слов выполнить `search_ontology`
   по тем же `keywords`. Результат кладётся в промпт ответа как ОТДЕЛЬНЫЙ блок
   «Карта онтологии» (книга/глава + аннотация-сниппет + страница + kind), рядом
   с блоком контентных `hits`, но помеченный как ориентир, а не как найденный
   ответ. Контентные `SearchHit` (то, что уходит в `ChatResponse.hits` и
   историю) НЕ трогаем — онтология не подмешивается в `collected`.

3. **Никаких новых LLM-вызовов.** Ontology-поиск использует те же `keywords`,
   что уже получены `_extract_keywords`. Дополнительный контекст просто
   расширяет существующее сообщение шага 3 (одна и та же `llm.chat_completion`).
   Бюджетный гард (`_budget`) остаётся как есть — токены слегка вырастут за счёт
   доп. блока в промпте, это ожидаемо и в рамках гарда.

4. **Флаг конфигурации `LLM_USE_ONTOLOGY`, по умолчанию включён.** Добавить в
   `config.py` булев флаг (env `LLM_USE_ONTOLOGY`, дефолт `true`/`1`). В
   `_run_inline` при выключенном флаге — поведение ровно как сейчас.

5. **Честность и лимиты.** Онтология-блок добавляется в промпт только если
   что-то реально нашлось; при пустом результате блок не добавляется, а в
   инструкции модели остаётся правило «не выдумывай источники». Лимит строк
   онтологии в контекст — небольшой константой (предлагается 6-8), сниппет
   обрезать по аналогии с `_hit_for_model` (~300 симв.), чтобы не раздувать
   промпт.

6. **read-only совместимость.** Всё через существующий `connection()` (уже
   `mode=ro`), новых записей нет — ограничение соблюдается автоматически.

## Риски и митигации

- **Дублирование SQL / рассинхрон логики** → вынести ядро в `ontology.py`, оба
  потребителя (роутер и чат) зовут одну функцию.
- **Раздувание промпта и рост токенов/стоимости** → жёсткий лимит строк
  онтологии (6-8) + обрезка сниппетов; блок добавляется только при непустом
  результате.
- **Модель путает аннотацию с фактическим контентом** → чёткое разделение
  блоков в промпте и инструкция «онтология = ориентир, не ответ».
- **Ломается вкладка «Онтология»/эндпоинт** → роутер остаётся тонкой обёрткой,
  JSON-контракт неизменен; проверить handшагом 9(г).
- **read-only нарушение** → используем существующий `connection()` (mode=ro),
  без записей.
- **Циклический импорт** (chat → ontology → db) → выносим в `app/ontology.py`,
  который зависит только от `db.py`; роутеры импортируют его, не наоборот.
- **Отсутствие `ontology_fts` в старом index.db** → обернуть вызов в чате в
  try/except (sqlite3.OperationalError → пустой результат, лог warning), чтобы
  чат не падал на индексе без онтологии.
