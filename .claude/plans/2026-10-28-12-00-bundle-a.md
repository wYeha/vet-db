# Пакет А: запасной путь онтологии, видовой буст, чистка `<br>` в сниппетах

## Цель и контекст
Онтология-экран (`POST /api/chat mode=ontology`, `chat.py::_run_ontology`) сейчас:
keywords (1 LLM) → `search_ontology` → `refine_ontology_hits` → плашки. Три дефекта:
1. Промах онтологии = пустой экран, хотя полнотекст по корпусу мог бы найти страницы.
2. Вид животного из вопроса теряется (keyword-шаг его не передаёт) → свиньи и птица
   смешаны («тилозин свиньям» → птичьи статьи).
3. В сниппетах виден текст «&lt;br&gt;» (сырой OCR с `<br>`, `html.escape` его экранирует).

Жёсткие рамки: без новых LLM-вызовов; `/api/ontology/search` и схема БД не меняются;
`index.db` read-only; никакой выдуманной классификации в данных (вид источника
вычисляется на лету из уже имеющегося текста, ничего не пишется).

Факты из репозитория: в корпусе 23 источника, по именам файлов онтологии — свиньи
(~12), птица (~8), нейтральные (`antimicrobial_therapy_handbook`, `anemia_and_drugs...`,
`pcr_test`, `streptococcosis_dissertation` и т.п.). Книг по КРС нет. Названия/аннотации
смешанные рус./англ. `sources.description` заполнен `load_annotations.py`.

## Архитектурные решения

### А1. Когда включать запасной путь
Только если после `refine_ontology_hits` список хитов ПУСТ (0 строк онтологии, пустой
`keywords`-результат, либо нет `ontology_fts`/`OperationalError` → `rows=[]`).
НЕ включать при «все хиты precise=False»: это валидные совпадения по аннотациям
(есть глава-кандидат), плашка «начало главы» информативна; полнотекст теми же keywords
после неудачи FTS внутри главы почти наверняка даст шум, а требование «не дублировать
плашки» запрещает смешивать. Альтернатива (дописывать fulltext к precise=False) —
в TODO как возможное развитие, не делать сейчас.

### А2. Реализация запасного пути (SQL-only)
Новая функция в `backend/app/ontology.py`: `fulltext_fallback_hits(db, keywords, limit=8) -> List[SearchHit]`.
- Рефакторинг без смены поведения: вынести из `_best_page` генератор строк-кандидатов
  `_page_candidates(db, match, source_id=None, lo=None, hi=None, limit=_CANDIDATES)`
  (тот же SELECT: page_index, source_id, source_title, markdown, `snippet(pages_fts,0,SNIPPET_ARGS)`,
  `ORDER BY rank`; `source_id`-условие опционально); `_best_page` использует его.
  Существующие тесты `test_ontology_refine.py` должны остаться зелёными как есть.
- Ступени: AND (`build_match_query`); если неплиблиографических хитов < `_MIN_STRONG_HITS`(3) —
  добор OR (`build_or_match_query`), дедуп по `(source_id, page_index)`, AND выше OR.
  Кандидатов брать с запасом (напр. 40 на ступень), затем фильтр и рерэнк, затем кап `limit`=8.
- Фильтр библиографии: `_is_bibliography(markdown)` — такие страницы исключаются; если
  после фильтра не осталось ничего, а литература была — вернуть пусто (решение: лучше
  честное «ничего», чем ссылка на список литературы; требование «если есть альтернатива»
  выполняется тривиально). Зафиксировать в тесте.
- Хит: `SearchHit(type="page", source_id, source_title, page_index, title=None,
  snippet=safe_snippet(snip), score=rank, precise=None, origin="fulltext")`.
  `precise=None` намеренно: фронт трактует только `precise===false` как «(начало главы)».
- Пустые keywords / нет терминов → `[]` без SQL. `OperationalError` (нет `pages_fts`) →
  ловит вызывающий в `_run_ontology` (лог warning, пусто).
- Лимит 8 плашек (= `_ONTOLOGY_QUERY_LIMIT`, привычная величина экрана).

### А3. Поле происхождения
`schemas.SearchHit`: `origin: Optional[Literal["ontology","fulltext"]] = None` (аддитивно,
как `precise`; старая история и обычный поиск → null). В `_run_ontology` помечать хиты
после refine `origin="ontology"` (а не внутри ядра — ядро/REST не трогаем). Фолбэк-ветка
`OperationalError` → тоже `"ontology"`. `_hit_key` не меняется.

### А4. Видовой буст — новый модуль `backend/app/species.py` (без LLM, без записи в БД)
- Словарь видов только по реально присутствующим в данных: `swine`, `avian`. КРС в
  данных нет → НЕ добавлять (иначе любой запрос про коров опустит все книги); структура
  словаря расширяемая, в TODO — «добавить `cattle` при появлении книг».
- `detect_query_species(text) -> frozenset[str]`: регулярные выражения по ИСХОДНОМУ
  сообщению пользователя (lower, `ё→е`), якорь `\b` в начале слова, с учётом ложных
  срабатываний. Рус. основы: swine — `свин(ь|ей|ья|ье|ин|к[аиу])`, `порос`, `хряк`,
  `свиномат`, `поросен`, `откорм`?(нет — не вид, не включать); avian — `птиц`, `кур(а|ы|е|у|ой|иц|ин|ят)`,
  `бройлер`, `цыпл`, `несушк`, `индейк`, `утк|утят`, `гус(ь|я|ей|ят)` и т.д. Англ.: `pig|swine|sow|piglet|boar`,
  `poultry|chicken|broiler|hen|turkey|duck|avian|bird`. ОБЯЗАТЕЛЬНЫЕ негативные случаи
  (в тестах): «свинец» (≠ swine), «курс», «курение», «густой», «утро», «бирд»…
  Несколько видов в запросе → множество из нескольких.
- `source_species(db) -> Dict[int, Optional[str]]`: один запрос
  `SELECT id, title, description FROM sources` (23 строки, кэш не нужен), на каждый источник
  считается число вхождений основ каждого вида в `title + " " + description` теми же
  регулярками (рус.+англ.). Вид присваивается, если top >= 2 И top >= 2 × runner-up;
  иначе `None` (нейтральный/смешанный: справочники, ПЦР, анемия). Прозрачно: это функция от
  имеющегося текста, ничего не хранится. Если `description` NULL (старый индекс) —
  только заголовок; ошибка/нет колонки (`OperationalError`) → `{}` (буст отключён).
  Единицы: источник-уровень, не глава (аннотации глав не используем — шум и рост SQL).
- `rerank_by_species(hits, query_species, src_species) -> List[SearchHit]`: СТАБИЛЬНАЯ
  сортировка по ключу яруса: 0 — вид источника ∈ query_species; 1 — вид неизвестен/нет
  source_id; 2 — вид источника иной. Ничего не отбрасывается, порядок внутри яруса
  сохраняется (Python `sorted` стабилен). Решение: три яруса вместо двух — нейтральные
  справочники не должны уходить ниже «чужого» вида; в отчёте/доке явно написать. Пустой
  `query_species` или пустой `src_species` → вернуть список без изменений (тот же порядок).
  Применяется ТОЛЬКО к хитам `type="page"`; прочие типы (если будут) сохраняют позицию.
- Где применять в `_run_ontology`: (а) к результату refine (≤8, пересортировка уже после
  дедупа), (б) для fulltext-пути — внутри/после `fulltext_fallback_hits` ДО капа 8
  (передавать вид параметром `rerank=Callable` или делать рерэнк на 40 кандидатах в
  `_run_ontology`; выбрать: `fulltext_fallback_hits(db, keywords, limit, species_key=None)`
  принимает опциональную функцию-ключ яруса, ядро остаётся независимым от species.py).
  Вид определяется из `message` (исходного), НЕ из keywords.
- Лог одной строкой: `species: query=%s tiers=%d/%d/%d`.

### А5. `<br>` в сниппетах
`snippets.py::safe_snippet`: ДО `html.escape` заменять `re.sub(r"<\s*br\s*/?\s*>", " ", s, flags=re.I)`
(покрывает `<br>`, `<br/>`, `<br />`, `<BR>`), затем схлопывать `[ \t]{2,}`/пробелы в один (не
трогая плейсхолдеры mark). Остальной HTML экранируется как раньше (`<img>`, `<script>` → `&lt;…`).
Крайний случай: FTS-`snippet()` режет по токенам, фрагмент может начаться с `br>` или
кончиться на `<br` (остаток тега). Добавить: срезать ведущий `^\s*/?\s*br\s*/?>` и хвостовой
`<\s*br\s*/?\s*$` (покрыть тестом; если сложно — оставить как известное ограничение в доке).
`ontology.py::_row` дублирует экранирование (`html.escape` + `chr(2/3)`): перевести на
`safe_snippet(r["snip"])` — ПРЕДВАРИТЕЛЬНО убедиться, что `_MARK_OPEN/_MARK_CLOSE` в snippets.py
== `chr(2)/chr(3)` (SQL в `_SQL` использует `char(2)/char(3)`); иначе привести в соответствие
без изменения SQL. Это даёт чистку и в онтологических сниппетах аннотаций, и в REST
`/api/ontology/search` (изменение только в тексте сниппета, контракт полей прежний — допустимо,
т.к. задача 3 требует «все сниппеты»). Помнить: `v-html` на фронте опирается на серверное
экранирование — не ослаблять.

### А6. Фронт (минимум)
`frontend/src/views/ChatView.vue::hitTitle`: для `h.type==='page' && h.origin==='fulltext'`
дописывать ` · вне онтологии` (по аналогии с «(начало главы)»); при наличии fulltext-плашек
над списком плашек — одна строка-подсказка «Темы нет в онтологии — показан полнотекстовый
поиск по книгам» (необязательно; если усложняет шаблон — ограничиться суффиксом).
`hitLink` не меняется. Старые сообщения из истории без `origin` — без пометки.

## Риски и митигации
| Риск | Митигация |
|---|---|
| Детектор вида даёт ложные срабатывания (`свинец`, `курс`, `густой`) | `\b`-якоря + явные формы слова, негативные тесты |
| Классификация книг по описанию неверна/шумна (смешанные книги) | Порог top>=2 и ×2 над вторым, иначе нейтрально; тест на реальном индексе со списком; НИЧЕГО не отбрасывается, максимум изменение порядка |
| Буст ухудшит выдачу, если пользователь пишет «свиньи», а нужная страница в птичьей/общей книге | Мягкая пересортировка по ярусам, все хиты остаются; нейтральные не наказываются |
| Fulltext-фолбэк шумный (OR по общим словам) | AND first, OR только как добор; keywords уже специфичные; лимит 8; фильтр литературы; плашка помечена «вне онтологии» |
| Литература на страницах выигрывает BM25 | Кандидатов 40 + `_is_bibliography`; «только литература → пусто» |
| Рефакторинг `_best_page` ломает этап 2 | Поведение неизменно, существующие тесты — гейт перед остальным |
| `<br>`-замена ломает XSS-гарантию | Замена только `<br>`-вариантов, до `escape`; тесты на `<img onerror>`/`<script>`/`<br onclick>`(последний должен быть экранирован, не удалён как br) |
| `ontology._row` на `safe_snippet` меняет текст REST-сниппета | Изменяется только чистка `<br>`; схема/поля не трогаются; отметить в доке |
| Старый индекс без `pages_fts`/`sources.description` | try/except `OperationalError`, деградация в пусто/без буста |
| Тесты на реальном индексе хрупки к пересборке | skipif + оговорка; запросы подбирать по текущим данным и ослаблять ассерты (≥1, порядок ярусов) |
| `origin` в сохранённой истории | Поле опциональное, старые записи без него — фронт без пометки |
| Регэксп `<br>` не покрывает `<br class=..>` | Осознанно: только заявленные формы; прочее остаётся экранированным |
